# Threat model

## Scope and assets

Protected assets are operator authority, merchant policy, recovery cohorts, customer-contact limits, original payment amounts, provider references, webhook state, API secrets, and judge-visible evidence. The demo uses synthetic customer IDs and Razorpay Test Mode only.

## Threats and controls

| Threat | Control | Verification |
|---|---|---|
| One judge changes another judge's run | Random per-login run ID; signed HttpOnly session; ownership check on every run API | Cross-run command test expects 403 |
| Forged operator approval | Server-authenticated operator identity; reason required; receipt binds run, role, reviewed version, policy digest, cohort digest, and timestamp | Receipt digest and actor assertions |
| Stolen or modified session token | HMAC-SHA256 token, constant-time signature comparison, eight-hour expiry, HttpOnly, SameSite=Strict, Secure in production | Valid, tampered, and expired token tests |
| Model proposes unsafe action | Model has read-only tools; Zod shape validation; deterministic policy rejects unsupported sets, amount changes, unsupported methods, extra contacts, opt-outs, or duplicates | Six adversarial policy cases |
| Duplicate command causes duplicate work | Client idempotency key plus persisted command receipt; optimistic versioning | Repeated-command test |
| Crash after external call creates a second Payment Link | Persist intent first; stable reference/idempotency key; reconcile by reference before create and after ambiguous failures | Stable-reference logic and integration checklist |
| Valid webhook from an unrelated payment captures this run | Resolve run from signed notes, then match persisted Payment Link ID, reference, and amount | Mismatched-artifact webhook test |
| Forged webhook | HMAC over untouched raw body; missing event ID rejected | Signature unit test and manual webhook test |
| Duplicate or out-of-order webhook regresses state | Atomic event-ID dedupe; paid is monotonic; late correlated failure is ignored | Duplicate and late-failure tests |
| Audit history edited silently | SHA-256 hash chain verified on local reads; append-only update/delete triggers in Supabase | Audit-chain test and migration inspection |
| Browser accesses service credentials | All provider and Supabase admin calls are server-only; secrets have no `NEXT_PUBLIC_` prefix except public Supabase URL | Production build and source inspection |

## Residual risks

- The shared buildathon access code is a demonstration authentication mechanism, not enterprise identity. Replace it with Razorpay/merchant SSO and role provisioning before production.
- A compromised server process or Supabase service role can still create new evidence or rewrite the run snapshot. Stronger non-repudiation would require an external append-only log or KMS-backed digital signatures.
- The deterministic adversarial dataset is generated by project authors, not an independent production distribution. Real deployment requires shadow-mode validation, drift monitoring, fairness review, and calibrated thresholds.
- Razorpay Test Mode proves API and webhook plumbing, not recoverability or economics in live payment traffic.
- The replay adapter proves state-machine properties; it does not send real customer messages.

## Secret and deployment requirements

Production requires `RECOVEROS_OPERATOR_ACCESS_CODE` and a high-entropy `RECOVEROS_SESSION_SECRET`. Rotate all secrets after the buildathon, limit the Supabase service role to this server deployment, enable HTTPS, protect deployment logs, and do not use real customer data in the demo.
